dune-game: Senior Dev Review

Repo: github.com/wr-max52/dune-game @ 06d6237 (M8 merge) · Reviewed 2026-10-26 · Godot 4.7.2 (pinned version, actually run)

TL;DR

  • I ran it. I cloned it, installed Godot 4.7.2, ran scripts/ci.sh (116/116 tests pass), then wrote my own probe scripts and rendered the demo scene under a virtual display.
  • The green suite is mostly self-congratulation. Most "proofs" are traces that hardcode their own outcomes and tests that read those traces back. The performance reports in particular measure nothing.
  • There is no playable game. The main scene prints a data summary to the console. The only visual scene (m1_demo) autopilots a camera across grey boxes, and none of the combat, AI, mission, or bartender systems are wired into any scene.
  • Several systems are broken in ways the tests can't see: the bolt scene doesn't even parse, the camera renders mirrored, the player spins forever after any mouse movement, the player walks through walls, the S key doesn't move you backward, and the squad AI assigns cover using the wrong index.
  • My opinion: stop adding milestones. Build one real scene that wires the existing systems together, then replace the trace "proofs" with measured frame times. The architecture (pure logic plus thin nodes, data layer) is a decent idea. The problem is that nothing was ever plugged in.

How I verified

  • ./scripts/ci.sh with real Godot 4.7.2 headless: all 8 traces were generated and 116 tests passed.
  • A probe script (review_probe.gd, run with godot --headless -s) that exercises each system outside the happy path. Every number below marked [measured] came from it.
  • xvfb-run plus the OpenGL3 renderer to screenshot m1_demo in FPV and TPV.

1. Critical: Performance

1.1 The performance "proofs" are fabricated, not measured

  • scenes/m8_playthrough.gd lines 214 and 234 literally write work += 25.0 and work += 30.0. The "worst_ms=30.000, over_budget=0" in m8_perf_report.txt is just the largest constant you typed in. No clock is read anywhere.
  • m4_frame_trace.gd feeds the streamer made-up load_ms: 18.0 values. Nothing actually loads, so the "frame time log" is arithmetic on invented numbers.
  • The anti-hitch invariant is a tautology. ChunkStreamer.update() caps spending at work_budget_per_frame, then the test asserts that spending never exceeded work_budget_per_frame. [measured] A chunk costing 10 full seconds of load work still reports within_budget=true. It can't fail.
  • Fix: measure real time with Time.get_ticks_usec() around actual work, plus Performance.get_monitor(Performance.TIME_PROCESS) and TIME_PHYSICS_PROCESS in a rendered run (xvfb works, I did it). Assert on p99 frame time, not on a number you chose.

1.2 The frame budget is wrong by 3x

  • 50 ms is about 20 fps. At 60 fps the whole frame budget is 16.7 ms, and a streaming system should get maybe 2 to 4 ms of it on the main thread.
  • As written, the streamer is allowed to burn 50 ms in a single frame. That isn't hitch prevention; that's a guaranteed 3-frame hitch.
  • Fix: do real loading off-thread with ResourceLoader.load_threaded_request() and only do tree insertion on the main thread, budgeted at a few ms.

1.3 The chunk streamer thrashes at window edges

  • There's no hysteresis, and unloading throws away partial progress. A player standing near a boundary makes chunks load, unload, and reload again forever.
  • [measured] A player jittering ±1.5 m around x=230 while standing still generated 5,436 ms of load work over 600 frames. That's about 9 ms every frame, indefinitely.
  • Fix: use separate load and unload radii (for example, load at 130 m and unload at 160 m), and keep a small LRU cache of recently unloaded chunks.

1.4 LLM, STT, and TTS will freeze the game once they're actually wired

  • OllamaClient._post() is a stub, and the bartender's interface is a synchronous pop_next(). If someone wires real HTTP or whisper.cpp into that shape, the main thread blocks for 0.5 to 5 seconds per turn.
  • Local inference also competes with the renderer for the same GPU and unified memory. Nobody has measured it (KNOWN_ISSUES admits "not yet measured").
  • Fix: make the client async now, before anything depends on it. Use an HTTPRequest node with a signal, or a Thread/WorkerThreadPool, and give the bartender a "thinking" state with a timeout.

1.5 Frame-rate-dependent gameplay

  • Weapon fire rate: the cooldown throws away its remainder each frame. [measured] The pistol (0.12 s) should fire 83 shots in 10 s. It actually fires 80 at 144 fps and 75 at 60 or 30 fps, so it's about 10% slower on most machines. Fix: _fire_cd_left += fire_cooldown() instead of =.
  • Camera vs body: the camera updates in _process while the body moves in _physics_process, so you get visible jitter on high-refresh monitors. Turn on physics interpolation (physics/common/physics_interpolation) or drive the camera from interpolated transforms.
  • Player rotation: rotate_y(rig.yaw) runs every render frame (see 2.3), so the spin speed also scales with fps.

1.6 Smaller performance smells (fine at slice scale, bad habits)

  • desired_active() allocates an array and a lambda and sorts every frame. _in_want() is O(n×m), and is_covered() is a linear scan. Use a dict or a spatial index.
  • WeaponActor.fire_at() calls load("weapon.gd") on every shot just to read an enum. Use a preload const.
  • SquadCoordinator uses Array.has() inside a loop (O(n²)).
  • Every trace builds its log with log += ... per frame, which is quadratic string growth. Use a PackedStringArray and "\n".join(), or write directly to the file.

2. Experience: Bugs and Player-Facing Problems

2.1 There is no game to play

  • The run/main_scene is main.tscn, which only prints data-layer counts. A player who presses F5 gets a grey window and console text.
  • m1_demo defaults to _auto = true and calls set_command() every frame, so human input is permanently ignored. use_external_command never resets.
  • Fire, block, reload, attack, interact, push-to-talk, and pause have no input actions at all. LAUNCH.md concedes this, yet PLAN says M0 through M8 are "done".
  • Input.mouse_mode is never set to captured, so mouse look runs into the screen edge.
  • The README claims a nobodywho addon was "added at M6". It isn't in the repo.
  • My opinion: this is the single biggest problem. "Done" was defined as "a headless trace prints the right words", and the trace scripts write those words themselves.

2.2 Camera renders mirrored

  • camera_rig.gd line 45 computes right = fwd.cross(UP) with fwd = -look, which flips the right vector. [measured] The basis determinant is -1.0, a reflection rather than a rotation.
  • Result: the world renders left-right mirrored, and mouse look feels inverted.
  • Fix: right = look.cross(Vector3.UP).normalized(), up = right.cross(look), Basis(right, up, -look). Or just use Transform3D().looking_at().
  • Add a test asserting is_equal_approx(basis.determinant(), 1.0).

2.3 The player spins forever after any mouse movement

  • camera_rig_node.gd line 37 calls _player.rotate_y(rig.yaw) every frame. rotate_y is relative, so any non-zero yaw keeps adding up.
  • [measured] A single 0.05 rad nudge left the body rotating continuously, about 0.97 rad later on.
  • Movement direction comes from -rotation.y, so WASD direction spins too.
  • Fix: _player.rotation.y = rig.yaw, and pick one sign convention (it's currently negated in one place and not the other).

2.4 Input map bugs

  • Added after the first review: no keyboard binding works at all. Every key event in project.godot uses "key_code", but Godot's property is "keycode". [measured] All eight actions load with keycode=0 (unset), so WASD, arrows, Space, V, Shift and C do nothing in-game. This is fixed on the review/senior-dev-fixes branch, with a regression test.
  • move_forward includes key code 83, which is S. Holding S triggers forward and back at once, which cancels out, so S does nothing. Only the Down arrow moves you backward.
  • toggle_view binds mouse button_index: 52, which doesn't exist. Middle mouse is 3, so LAUNCH.md's "or mouse middle button" is wrong.
  • Crouch uses is_action_just_pressed, so it lasts exactly one physics frame. It should be held or toggled.

2.5 Player movement ignores physics

  • The player CharacterBody3D has no CollisionShape3D, so move_and_slide() collides with nothing.
  • Even with a shape it wouldn't help: every frame starts with global_position = controller.body_pos, which throws away whatever move_and_slide resolved. The pure controller is the authority and it knows nothing about the world.
  • [measured] Walking into a wall at z=3 for 1 s left the player at z=3.53, straight through it.
  • Ground is hardcoded to y=0 (ground_y is always passed as 0.0), so you can't stand on cover boxes, ramps, or terrain.
  • The spawn position y=0.9 is overwritten on frame 1 because body_pos starts at the origin.
  • The player has no mesh. In my TPV screenshot there's no character on screen at all, just a grey floor.
  • There's no WorldEnvironment, so faces facing away from the light render pure black (visible in my FPV screenshot).
  • Fix: let the controller compute only velocity, set velocity, call move_and_slide(), then read back is_on_floor() and global_position.

2.6 Blasters cannot hit anything

  • bolt.tscn doesn't parse. [measured] Godot reports "Parse Error: Unknown tag 'sub_resource'" because the sub_resource is declared after a node, so load() returns null.
  • Even if it parsed, the Area3D has no CollisionShape3D, so body_entered can never fire. The comment's collision layers are never set either.
  • WeaponActor.bolt_scene and bolt_parent are never assigned anywhere in the codebase, so _make_bolt() always returns early.
  • bolt.global_position is set before add_child, which Godot warns about.
  • Tests load bolt.gd directly, never the .tscn, which is exactly why none of this was caught.
  • At 48 m/s with no shape cast, fast bolts will also tunnel through thin geometry once they do have a shape. Use a raycast per step.

2.7 Melee and duelist: there's no skill in "timed deflection"

  • The duelist calls start_block() then intercept_bolt() in the same frame, so its deflection is instant and perfect whenever it's off cooldown. That isn't timing; it's a coin with one side.
  • It never calls end_block(). After the first parry the blade stays in BLOCK forever, and _block_elapsed grows past the deflect window. [measured] It parried only 4 of 20 swings, and the blade sat in BLOCK draining to 7 stamina.
  • The M3 trace's "blows land so the duelist is killable" only happens because of that bug.
  • The trace applies full damage on any non-PARRY result, so a blocked blow still does 16 damage. Blocking is cosmetic.
  • A deflection refunds stamina, so a skilled player can block forever. That might be intended, but make it deliberate.
  • PARRY_CD := PARRY_WINDOW means two names for one 0.2 s value. Tune them separately.
  • The data field duelist_deflect_fraction: 0.34 in the mission JSON is never read.

2.8 AI bugs

  • The squad coordinator measures distance from cover node i to member i (_member_pos(i) uses the cover index), not from the member being assigned. Assignment ends up in index order regardless of position.
  • [measured] With member 0 next to node 1 and member 1 next to node 0, it returns [0, 1] instead of [1, 0], so both troopers run 100 m across the map.
  • The tests never caught it because every fixture puts member i exactly on node i.
  • Even fixed, greedy nearest-free assignment is order-dependent. Fine for 4 troopers, but know that it isn't optimal.
  • Cover is chosen by distance only, ignoring where the player is. A "cover" node on the player's side is just standing in the open.
  • TrooperBrain.update() overwrites target_position (the player) with the cover position, so the trooper forgets who it's shooting at.
  • Nothing ever calls TrooperBrain.fire(). The M2 trace's "return fire" is a separate hardcoded timer doing 5 damage, not the brain.
  • Nothing moves the trooper in-game. self_position is only advanced by the trace script.

2.9 The LLM bartender doesn't hear the player

  • respond(text_request, ...) never uses text_request. [measured] "where is the crate?" and "I hate you" get the identical reply. The "guardrail" holds because the input is discarded, which is like securing a door by removing the building.
  • OllamaClient has no pop_next(), so it doesn't implement the interface the bartender calls. build_request() sends only the system prompt with no user message and no history. _post() returns "".
  • It defaults to llama3, but KNOWN_ISSUES says the planned model is Qwen3 4B.
  • parse_response() crashes if the JSON is an Array or content is null. It also returns text: "" on error, which the bartender would display as an empty reply instead of falling back.
  • The fallback cycle has an off-by-one. [measured] The sequence is A, B, C, A, A, B, C, so the first line repeats.
  • bartender.json lists fallback lines under fallback_lines, which the loader never reads (it only reads dialogue). Every trace hardcodes the tools and fallback lines in GDScript, breaking the project's own "nothing outside content/core" rule.
  • memory = memory_in aliases the caller's dict and mutates it in place, while the API pretends to return a new one.
  • give_rumor stores whatever text the model said as "the rumor", so a prompt-injected reply becomes persistent memory that gets saved to disk.
  • call_guards is an allowed tool that any persuasive player can trigger. An allowlist is not a guardrail for intent; you need rate limits and disposition gating.
  • KokoroVoice.synthesize() always returns null, and signature() is hash(), which isn't stable across engine versions. Calling M6 "Kokoro voice" is generous.

2.10 Voice input

  • When whisper is unavailable, capture() "falls back to typed" by stringifying the audio sample. [measured] A PackedByteArray becomes the literal text '[1, 2, 3, 4]' and gets sent to the bartender as if the player typed it.
  • now_ms is never advanced, so the real press()/release() path always reports 0 ms latency. Every latency number in the M7 trace is a hardcoded argument.
  • Whisper "transcription" is a dictionary lookup of canned strings, and forceload() succeeds as long as the model filename is non-empty.

2.11 Save, mission, and health

  • Save: Godot's JSON parser returns every number as a float, so credits and the mission's int fields come back as floats and only survive because of scattered int() casts. Nothing is type-checked or validated on load.
  • remember_in_bartender() crashes if new_game() wasn't called first, and a short player_position array crashes get_player_position().
  • Writes aren't atomic, so a crash mid-save corrupts the only save. Write to .tmp and then rename.
  • version: 1 is written but never checked, and there's no migration path.
  • Mission: started is never set true. Phase.ACCEPT and Event.ACCEPT share a name. from_save() trusts enemies_total from the save over the config, so edited data won't apply to old saves.
  • trooper_hp and duelist_hp in the mission data are never used.
  • Health: int() truncation drops fractional damage. [measured] Ten hits of 0.9 damage do 0 total.
  • heal() works on dead entities (hp goes up while _alive stays false), and on_death is never connected anywhere.

2.12 Tests and CI give false confidence

  • Trace scripts decide the outcome, write it to a file, and then a test greps the file for it. That's circular. When a test "proves" something its own fixture asserted, it proves nothing.
  • ci.sh prints the pinned and actual versions but never compares them, so the "pin check" can't fail.
  • test_results/ is never cleaned before a run, so a stale trace from yesterday satisfies the "file exists" gate even if today's script crashed. Trace output goes to /dev/null, so script errors are invisible, and Godot usually exits 0 on GDScript errors anyway.
  • There's no .github/workflows, so "CI" is a local script you have to remember to run.
  • record.sh calls /usr/sbin/avfoundation, which doesn't exist. The device listing should be ffmpeg -f avfoundation -list_devices true -i "", and the script grabs the first video device, which is often the webcam, not the screen.

2.13 IP exposure (opinion, but take it seriously)

  • The banned-term list checks for "mandalorian" and "jar jar". Meanwhile the data ships a faction literally named "Imperial Remnant", which is a canonical Star Wars faction name, alongside blasters, troopers, an energy-blade duelist, and a desert spaceport cantina. The repo is named "dune-game".
  • Individually these are generic. Together, in a public repo, the scan is a fig leaf. Rename the faction, add "imperial", "jedi", "sith", "lightsaber", "stormtrooper", "dune", "arrakis", and "spice" to the scan, and consider making the repo private until the skin layer exists.
  • I'm not a lawyer; this is a risk flag, not legal advice.

3. Style and Maintainability

  • Milestone tags in code comments ("M2", "M5, deferred from M4", "the M7 decision") are already stale and will rot. That history belongs in git and the CHANGELOG, not in docstrings.
  • Docs outweigh code. There are about 840 lines of CHANGELOG, DECISIONS, and KNOWN_ISSUES narrative against about 1,500 lines of game logic, and the docs contradict reality: README still says "No gameplay yet (M0)" next to "M0-M8 are done".
  • Eight copy-pasted trace harnesses share identical _build/_process/file boilerplate, and ci.sh has eight copy-pasted blocks. One generic runner would replace them.
  • A var named log in every trace shadows the built-in log(). It works, but it's a trap.
  • Weak typing: var weapon, var client, var blade, and var brain have no types and no class_name, so nothing gets editor autocomplete or static checks. Add class_name to each system and type everything.
  • Mixed load() and preload(): several classes load() scripts at runtime inside functions. Prefer preload consts.
  • Magic numbers: stamina regen 18.0, recovery 0.15 and 0.4, jump height 0.6, and the 0.5 s regen delay should be config or named consts, especially since you built a data layer for exactly this.
  • core_content.gd has two near-duplicate JSON readers. _read_text bypasses root_path(), the persona path relies on a fragile .replace("dialogue/", ""), and weapons and factions are stored even when empty, unlike locations and missions.
  • Logging: push_warning on every camera toggle spams the warning log for a normal action. Use print_verbose or nothing.
  • Doc comments (##) are used inside function bodies, where they don't attach to anything. Use # there.
  • Raw key codes like 4194320 in project.godot make bugs like the S binding invisible. Edit the input map in the editor, or comment each code.
  • camera_rig.gd types cos(pitch) as Variant. It should be float.

Recommended order of fixes

  1. Fix bolt.tscn, the camera basis, rotate_y, the S binding, and player collision. These are about an hour of work and unblock everything else.
  2. Build one real level scene: player, two troopers, a duelist, the bartender, and the fixer, with all inputs bound. Make it the main scene.
  3. Replace the hardcoded perf numbers with measured frame times in an xvfb run, and fail CI on a p99 above 16.7 ms.
  4. Make the LLM path async and actually pass the player's text and conversation history.
  5. Fix the squad index bug and duelist end_block, and write tests where fixtures don't line up perfectly.
  6. Harden CI: a real pin comparison, a clean test_results/, no output to /dev/null, and a GitHub Actions workflow.
  7. Then do the style cleanup.
